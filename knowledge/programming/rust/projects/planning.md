# Rust — Как планировать проект

Планирование превращает «хочу написать утилиту» в «утилита написана, протестирована, задокументирована и опубликована». Здесь — пошаговый процесс: требования, архитектура, ошибкоустойчивость, тесты, производительность, публикация.

---

## 1. Требования (requirements)

### Документ требований: одна страница

Перед кодом — короткий набор требований. Формат: **функциональные** (ЧТО делает) и **нефункциональные** (КАК делает).

| Тип | Пример |
|-----|--------|
| Функциональное | «Утилита принимает `--file` и выводит количество строк» |
| Функциональное | «При отсутствии файла выводит понятную ошибку и код возврата 2» |
| Нефункциональное | «Работает за O(n) по времени» |
| Нефункциональное | «Не требует прав администратора» |
| Нефункциональное | «Шифрование через стандартный криптографический примитив» |

### Правило «задай три вопроса» перед проектом

1. **Какой ввод?** (CLI-флаги? файл? поток? сеть?)  
2. **Какой вывод?** (терминал? файл? JSON? HTTP-ответ?)  
3. **Что происходит при ошибке?** (паника? сообщение с кодом возврата? повтор? `Result`?)

Записав ответы на эти три вопроса, вы уже описали `main`-функцию:

```rust
// ввод: --file <PATH>, --level <L>
// вывод: таблица статистики
// ошибка: eprintln + exit(2), иначе Ok
fn main() -> anyhow::Result<()> { ... }
```

### Формулировка задач (issue breakdown)

Для большого проекта разбейте на маленькие вехи:

- [ ] Веха 1: читает файл и печатает число строк
- [ ] Веха 2: фильтр по уровню
- [ ] Веха 3: группировка по часу
- [ ] Веха 4: параллельная обработка
- [ ] Веха 5: тесты и документация

Каждая веха — это **законченная, запускаемая, тестируемая** единица. Никогда не планируйте «всё сразу»: одна веха — один коммит с проходящими тестами.

## 2. Архитектура и структура

### Бинарник или библиотека?

```txt
Правило: сначала lib, потом bin.
```

Тяжелую логику выносите в `src/lib.rs` (или модули), а `src/main.rs` оставляйте тонким — только ввод/вывод. Это даёт:

- юнит-тесты на `lib` без запуска бинарника;
- переиспользование логики в других инструментах;
- публикацию крейта на crates.io с полноценным API.

```txt
my_project/
├── Cargo.toml
├── src/
│   ├── lib.rs        ← логика, pub API
│   ├── main.rs       ← разбор аргументов + вызов lib
│   └── ...
└── tests/
    └── integration.rs
```

### Слои бизнес-логики (для web)

| Слой | Задача | Крейты |
|------|--------|--------|
| routes / handlers | HTTP-вход, экстракторы | axum |
| services | бизнес-правила, оркестрация | — |
| repos / storage | доступ к данным | sqlx, rusqlite |
| models | структуры и сериализация | serde |

Нижние слои не знают о верхних: `service` не зависит от `axum`.

### Модульность

- Один модуль = одна ответственность (парсинг, вывод, доступ к БД);
- Публичный API — только через `pub`, внутренние детали приватны;
- `pub(crate)` — для внутренней видимости между модулями;
- Именование: `utils.rs`, `error.rs`, `models/`.

## 3. Ошибкоустойчивость (fail-safe)

### Стратегия обработки ошибок

| Контекст | Подход |
|----------|--------|
| Код, где ошибка «не должна» случиться и её невозможно обработать | `panic!` / `expect` |
| Обычная логика, ошибка ожидаема | `Result<_,_>` + `?` |
| Ошибки ввода пользователя | возврат `Err` + объяснение, без паники |
| Проверка инвариантов в тестах | `assert!` / `assert_eq!` |
| Граница приложения (main) | `anyhow::Result` + контекст |

Правила:

1. **Никогда не `unwrap` ввод пользователя** — файл может не существовать, строка может не быть числом.
2. **`unwrap` допустим только там, где ошибка действительно невозможна** (между собственными инвариантами) и с комментарием почему.
3. **Ошибка несёт контекст**: «не удалось открыть `config.toml` в `/app`» лучше, чем «IO error».
4. **Пользовательская ошибка не роняет программу паникой**, а печатается в stderr с кодом возврата.

```rust
fn read_first_line(path: &str) -> anyhow::Result<String> {
    // anyhow::Context добавляет пока недоступный контекст
    let content = std::fs::read_to_string(path)
        .with_context(|| format!("не удалось прочитать файл {path}"))?;
    let line = content.lines().next()
        .context("файл пуст")?;
    Ok(line.to_string())
}
```

### Паника и panic=abort

- Для CLI по умолчанию `panic = "unwind"` (можно ловить и чистить);
- Для сервисов, где панику переживать нельзя, — `panic = "abort"` в release;
- `cargo test --release` замечает паники в тестах.

## 4. Тестирование

### Пирамида тестов

```
        /  doc  \      ← примеры в документации
      / integration \   ← тесты публичного API через lib
    /     unit        \ ← тесты отдельных функций внутри модулей
```

### Unit-тесты (`#[cfg(test)]` внутри модулей)

Тестируют одну функцию в изоляции, без сайд-эффектов. Размещаются в том же файле, что и код.

```rust
// внутри math.rs
fn add(a: i32, b: i32) -> i32 { a + b }

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn test_add() { assert_eq!(add(2, 2), 4); }
    #[test]
    fn test_add_negative() { assert_eq!(add(-1, 1), 0); }
}
```

### Integration-тесты (`tests/`)

Проверяют публичный API как «внешний потребитель». Для web — через `tower::ServiceExt::oneshot`, для CLI — через `std::process::Command`.

```rust
// tests/calculator.rs
use my_project::calc;

#[test]
fn integration_priority() {
    assert_eq!(calc("2 + 3 * 4"), 14);
}
```

### Doc-тесты (в `///` комментариях)

Код в документации выполняется `cargo test` — гарантирует, что примеры не устаревают.

```rust
/// Складывает два целых числа.
///
/// ```
/// use my_project::calc;
/// assert_eq!(calc::add(2, 2), 4);
/// ```
pub fn add(a: i32, b: i32) -> i32 { a + b }
```

### Инструменты

| Фреймворк | Назначение |
|-----------|------------|
| `assert_eq!`, `#[test]` | базовые тесты (std) |
| `pretty_assertions` | наглядные diff при падении |
| `proptest` / `quickcheck` | property-based (случайные входы) |
| `insta` | snapshot-тесты (для парсеров, рендереров) |
| `criterion` | бенчмарки |
| `cargo-llvm-cov` / `tarpaulin` | покрытие |

### Таксономия «что тестировать»

- граничные случаи (пустой вход, максимум, ноль);
- ошибки (невалидные данные → `Err`);
- «золотые» примеры (известный вход → известный выход);
- идемпотентность (устойчивость к повторам);
- конкурентность (для пулов/серверов).

## 5. Производительность

### Профилирование: сначала мерить, потом оптимизировать

Цикл: **замер (criterion / hyperfine) → найти узкое место → оптимизировать → перемерить**.

| Инструмент | Что делает |
|------------|------------|
| `criterion` | точные бенчмарки функции |
| `hyperfine` | сравнение CLI-бинарников |
| `cargo flamegraph` | где тратится время |
| `cargo bloat` | размер бинарника |
| `valgrind` / `perf` | память и CPU (для C-уровня) |

### Типичные оптимизации в Rust

1. **Release-флаги**: `opt-level = 3`, `lto = true`, `codegen-units = 1` в `[profile.release]`;
2. **Уберите ненужные клоны**: заимствуйте, не копируйте; `clone` дорог;
3. **Преаллокация**: `Vec::with_capacity(n)`, `String::with_capacity`;
4. **Не перевыделяйте буферы**: переиспользуйте между итерациями;
5. **Бинарные форматы** вместо текстовых для больших данных (bincode, rkyv);
6. **`rayon`** для CPU-параллелизма на больших данных;
7. **Избегайте monomorphization explosion** для огромных generic-цепочек (редко).

### Память и аллокации

- `String`/`Vec` — куча; `&str`/`&[T]` — заимствование без аллокации;
- `Box<T>` — единичная аллокация; `String` при росте перевыделяется;
- Итераторы (`.map`, `.filter`) не создают аллокаций — цепочки бесплатны;
- `Vec::collect()` создаёт аллокацию — минимизируйте при горячих циклах.

## 6. Чистота и стиль

```bash
cargo fmt            # автоматическое форматирование
cargo clippy -- -D warnings   # линтер, treat warnings as errors
cargo doc --open     # документация + doc-tests
```

- `clippy` ловит: излишние клоны, `unwrap` в неподходящих местах, неэффективные преобразования;
- `-D warnings` заставляет исправить все замечания перед публикацией;
- `cargo fmt --check` в CI проверяет форматирование без изменений.

## 7. Публикация (cargo publish)

### Перед публикацией

- [ ] `name` уникален на crates.io (проверьте `cargo search <name>`);
- [ ] `version` не повторяется (каждая публикация — новая версия);
- [ ] `license` задана (например, `MIT OR Apache-2.0`);
- [ ] `README.md` на верхнем уровне;
- [ ] `description` и `repository` заполнены;
- [ ] `cargo test` зелёный;
- [ ] `cargo clippy -- -D warnings` чист;
- [ ] `cargo publish --dry-run` прошёл (пакует, проверяет).

```toml
[package]
name = "my_project"
version = "0.1.0"
edition = "2021"
description = "Краткое описание"
license = "MIT OR Apache-2.0"
repository = "https://github.com/user/my_project"
```

### Команды

```bash
cargo login <TOKEN>      # один раз, токен с crates.io
cargo publish --dry-run  # локальная проверка
cargo publish            # публикация
cargo publish -p my_crate  # определённый крейт в workspace
```

### Управление версиями (semver)

| Изменение | Версия |
|-----------|--------|
| Исправление бага (backward-compatible) | +патч: 0.1.0 → 0.1.1 |
| Новая фича (backward-compatible) | +минор: 0.1.0 → 0.2.0 |
| Ломающее изменение API | +мажор: 0.1.0 → 1.0.0 |

Правило zero-версий: пока `0.x`, минорное изменение может ломать (в отличие от `1.x`).

### Хорошие практики публичного API

- `#![warn(missing_docs)]` — принуждает документировать всё публичное;
- Типы `Error` через `thiserror` — потребитель может `map_err`;
- Минимизируйте публичное — только то, что нужно потребителю;
- `#[must_use]` на функциях, чей результат нельзя игнорировать.

## Чек-лист планирования проекта (сводный)

- [ ] Есть документ требований (ввод/вывод/ошибки)
- [ ] Разбит на вехи, каждая самостоятельно тестируема
- [ ] Логика в `lib`, bin тонкий
- [ ] Слои не перепутаны (для web)
- [ ] Обработка ошибок: `Result`, а не `unwrap` на вводе
- [ ] Юнит-тесты на все нетривиальные функции
- [ ] Интеграционные тесты через публичный API
- [ ] Doc-тесты в публичной документации
- [ ] `cargo fmt`, `cargo clippy -- -D warnings` чисты
- [ ] Release-профиль настроен
- [ ] README + license + description для публикации
