# Rust — Каталог учебных проектов

Здесь — расширенный каталог из 20+ учебных проектов: от простой CLI-утилиты до полноценного web-сервиса. Каждый проект разобран по единой схеме: **постановка задачи → архитектура → ключевые крейты → этапы реализации → чек-лист**. Проекты расположены в порядке роста сложности и привязаны к юнитам базы.

## 1. CLI: генератор паролей «pwn»

**Постановка задачи.** Командная утилита генерирует случайные безопасные пароли. Пользователь задаёт длину, набор символов, число паролей; утилита выдаёт пароли и оценку их силы. Это первый «настоящий» проект: у него есть вход (аргументы), обработка (генерация) и выход (вывод).

**Архитектура.**

```
main.rs          — разбор аргументов, точка входа
lib.rs           — логика генерации (чистая, тестируемая)
  └─ PasswordSpec { length, chars }   — параметры
  └─ generate(spec) -> String         — генерация
  └─ strength(pw) -> Strength         — оценка (слабо/ок/сильно)
```

**Ключевые крейты:** `clap` (аргументы), `rand` (случайность), `serde_json` (вывод в JSON, опционально).

**Этапы.**
1. Создайте `cargo new pwn --lib` и добавьте `[lib]` + `[[bin]]` в Cargo.toml;
2. Напишите функцию `generate` — выбор случайного символа из набора;
3. Реализуйте оценку силы по правилам (длина, наличие цифр и спецсимволов);
4. Подключите `clap` с флагами `--length`, `--nums`, `--symbols`, `--count`;
5. Добавьте `--json` и цветовой вывод.

**Чек-лист.**
- [ ] Разделение на `lib` (логика) и `bin` (ввод-вывод)
- [ ] Ни один символ: генерация не паникует, а возвращает `Err`
- [ ] `clap` отдаёт понятные ошибки при неверных флагах
- [ ] Юнит-тесты на `generate` и `strength`
- [ ] `cargo clippy` и `cargo fmt` без замечаний

## 2. CLI: файловый менеджер «fman»

**Постановка задачи.** Утилита для работы с файлами в терминале: `ls`, `cat`, `cp`, `mv`, `rm`, `mkdir`, `tree`. Отдельный флаг `--color` включает подсветку файлов/директорий.

**Архитектура.**

```
main.rs
  └─ dispatcher  — match по подкоманде (ls/cat/cp/...)
  └─ commands/   — по модулю на подкоманду
      ls.rs, cat.rs, cp.rs, mv.rs, rm.rs, tree.rs
  └─ util.rs     — общие хелперы (пути, цвета, ошибки)
```

**Ключевые крейты:** `clap`, `std::fs`, `std::path`, `owo-colors` (цвета).

**Этапы.**
1. Реализуйте `ls` через `fs::read_dir` с сортировкой;
2. Реализуйте `cat` через `fs::read_to_string` (и бинарный режим);
3. Реализуйте `cp`/`mv` через `fs::copy` / `fs::rename`;
4. Реализуйте `mkdir -p` (рекурсивное создание);
5. Реализуйте `tree` — рекурсивный обход директорий;
6. Добавьте цвета по типу записи.

**Чек-лист.**
- [ ] Каждая подкоманда — отдельная тестируемая функция
- [ ] Ошибки вида «файл не найден» не приводят к панике
- [ ] `tree` не падает на циклических symlink'ах (считает в глубину)
- [ ] Пути с пробелами и юникодом обрабатываются корректно
- [ ] Интеграционные тесты вызывают бинарник через `std::process::Command`

## 3. Парсер CSV «csvread»

**Постановка задачи.** Библиотека для чтения и записи CSV: парсинг строк с учётом кавычек, экранирования и переносов внутри полей; `Reader` как итератор по строкам; `Writer` для записи; доступ к колонкам по имени заголовка.

**Архитектура (ключевая идея — итератор).**

```
pub struct Reader<R: Read> { source: R, ... }
impl<R: Read> Iterator for Reader<R> { type Item = Result<Vec<String>, CsvError>; }

pub struct Writer<W: Write> { writer: W, ... }
impl<W: Write> Writer<W> {
    pub fn write_record(&mut self, record: &[&str]) -> io::Result<()>;
}
```

**Ключевые крейты:** только `std` (для сравнения можно подключить `csv`).

**Этапы.**
1. Напишите тип `CsvError` (этоerror-подобный вручную) с вариантами `Io` и `Parse`;
2. Реализуйте парсер одного поля с учётом `"..."` и `""` как экранированного `"`;
3. Реализуйте `Reader::next` — чтение одной записи (полей может быть больше одной строки);
4. Реализуйте `Writer`;
5. Добавьте `headers()` и доступ к колонке по имени.

**Чек-лист.**
- [ ] Корректно парсятся поля с запятой и переносом внутри кавычек
- [ ] Экранирование `""` внутри кавычек обработано
- [ ] `Reader` не паникует на кривом вводе, а возвращает `Err`
- [ ] Тесты покрывают: пустой файл, одну строку, многострочные поля, юникод
- [ ] `cargo doc` документирует публичное API

## 4. HTTP-клиент «miniq»

**Постановка задачи.** Консольный HTTP-клиент в духе `curl`: `GET`, `POST`, заголовки, тело, вывод статуса и раскраска ответа. Учит работе с внешними сервисами и обработке сетевых ошибок.

**Архитектура.** Простой итеративный: одна команда → один запрос → один ответ.

```
main.rs
  └─ Args (clap)          URL, -X, -H, -d, --json, --headers
  └─ request()            возвращает Response { status, headers, body }
  └─ render()             цветной вывод
```

**Ключевые крейты:** `reqwest` (sync), `clap`, `colored`, `serde_json`.

**Этапы.**
1. Реализуйте `GET` и вывод статуса + тела;
2. Добавьте `POST` с телом (`-d`);
3. Добавьте заголовки запроса (`-H`);
4. Добавьте `--json` (парсинг и подсветка JSON) и `--headers`;
5. Раскрасьте статусы: 2xx зелёный, 4xx жёлтый, 5xx красный.

**Чек-лист.**
- [ ] Сетевые ошибки (нет соединения, DNS) дают осмысленный вывод и код возврата ≠ 0
- [ ] Некрасивый вход (не URL) отсекается рано
- [ ] Тест на локальном тестовом сервере (см. раздел «web-сервер»)
- [ ] Таймаут запроса задаётся

## 5. Web-сервер статики на TcpListener

**Постановка задачи.** Минимальный веб-сервер на чистых `TcpListener`/`TcpStream` без фреймворка: принимает HTTP-запрос, отдаёт файл из папки или 404. Тренирует понимание протокола HTTP «на уровне байтов».

**Архитектура.**

```
main.rs
  └─ accept_loop()        — TcpListener::bind + цикл accept
  └─ Connection::handle() — читает запрос, возвращает ответ
  └─ http.rs              — parse_request, status_line, headers
  └─ mime.rs              — расширение → MIME-тип
```

**Ключевые крейты:** только `std` (`net`, `io`, `fs`); для асинхронности позже можно добавить `tokio` + `hyper`.

**Этапы.**
1. `bind("127.0.0.1:7878")` и простейший ответ `200 OK`;
2. Разберите строку запроса (метод, путь, версия);
3. Сопоставьте путь с файлом в корне сервера;
4. Определите MIME по расширению (`.html`, `.css`, `.js`, `.png`, ...);
5. Верните тело файла или `404 Not Found`;
6. Добавьте вывод `index.html` для `/` и логирование.

**Чек-лист.**
- [ ] Ответ корректно завершается `\r\n\r\n`
- [ ] Небольшой обработчик после каждого `accept` (однопоточный) не блокирует всё — либо многопоточность через `thread::spawn`
- [ ] Путь с `..` не выходит за корень (защита от path traversal)
- [ ] Проверка через `curl -v` на реальном порту
- [ ] Интеграционный тест поднимает сервер в потоке и опрашивает его

## 7. Key–value хранилище «kvstore»

**Постановка задачи.** In-memory key-value база в духе Redis: `SET`, `GET`, `DEL`, `EXPIRE`, `TTL`, `KEYS`, `FLUSHALL`, с персистентностью на диск и TCP-интерфейсом.

**Архитектура.**

```
src/
  ├─ main.rs        — запуск, TCP-listen
  ├─ server.rs      — обработка одного соединения (построчный протокол)
  ├─ db.rs          — хранилище: HashMap + TTL-очередь
  └─ persistence.rs — snapshot на диск, загрузка при старте
```

**Ключевые крейты:** `tokio`, `serde`/`bincode`, `tokio-util` (LineDelimited codec).

**Этапы.**
1. Базовые `SET`/`GET`/`DEL` на `HashMap`;
2. TTL: `BinaryHeap` по времени истечения + фоновый поток очистки;
3. `KEYS`, `FLUSHALL`;
4. Снапшот на диск по таймеру и при graceful shutdown;
5. Построчный TCP-протокол (`*3\r\n$3\r\nSET\r\n...` — mini-RESP).

**Чек-лист.**
- [ ] Истёкшие ключи не возвращаются после `TTL`
- [ ] Конкурентный доступ через `Arc<Mutex<Db>>` корректен
- [ ] Снапшот атомарен (пишем во временный файл, потом переименовываем)
- [ ] Один сокет не замораживает другие (spawn на соединение)
- [ ] Тест: SET → EXPIRE → sleep → GET = None

## 8. Конкурентный пул задач «workerpool»

**Постановка задачи.** Библиотека пула воркеров: N потоков выполняют M задач из очереди. Две реализации — через `std` (`thread` + `mpsc`) и через `rayon` (параллельный итератор).

**Архитектура (std-реализация).**

```
pub struct Pool {
    sender: mpsc::Sender<Job>,        // очередь задач
    workers: Vec<Worker>,             // consumе'ры
}
struct Job(Box<dyn FnOnce() + Send>); // задача как замыкание
```

**Ключевые крейты:** `std` (`thread`, `sync::mpsc`), `rayon` (вариант), `crossbeam` (необязательно).

**Этапы.**
1. Реализуйте структуру `Pool` с `new(n)` и `execute(f)`;
2. Создайте N потоков, каждый ждёт задачу из канала;
3. Добавьте `join()` — ожидание завершения всех задач;
4. Сравните с `rayon` версией: `inputs.par_iter()`.
5. Добавьте возврат результатов через второй канал.

**Чек-лист.**
- [ ] Каждая задача выполняется ровно один раз
- [ ] Ошибка внутри задачи не роняет пул
- [ ] Тест с 100 задачей и 4 воркерами: все выполнены
- [ ] `join()` не зависает
- [ ] Нет data races (компилятор это уже гарантирует)

## 9. Парсер арифметики «arith»

**Постановка задачи.** Калькулятор выражений `2 + 3 * (4 - 1)` → `11` с приоритетами, скобками, унарным минусом. Тренирует рекурсивный спуск и `enum` как AST.

**Архитектура.**

```
src/
  ├─ lexer.rs   — Token { Number(f64), Plus, Minus, Star, Slash, LParen, RParen }
  ├─ ast.rs     — Expr { Number, BinOp{ op, l, r }, Neg }
  ├─ parser.rs  — рекурсивный спуск: expr → term → factor
  └─ eval.rs    — вычисление AST
```

**Этапы.**
1. Токенизатор (числа, `+ - * /`, скобки);
2. Грамматика с приоритетами: `expr`(`+`/`-`) → `term`(`*`/`/`) → `factor`(число/скобка/минус);
3. Построение AST;
4. Вычисление;
5. Юнит-тесты: приоритет, скобки, ошибки («неожиданный токен»).

**Чек-лист.**
- [ ] `2 + 3 * 4` = 14, `(2 + 3) * 4` = 20
- [ ] Унарный минус: `-5 + 3` = -2
- [ ] Деление на ноль даёт `Err`, а не `NaN`
- [ ] Невалидный ввод (`2 ++ 3`) даёт осмысленную ошибку
- [ ] Покрытие юнит-тестами ключевых случаев

## 10. Markdown → HTML «md2html»

**Постановка задачи.** Конвертер Markdown в HTML: заголовки, жирный/курсивный, списки, кодовые блоки, ссылки, изображения, таблицы.

**Архитектура.** Поблочный парсер: разбиваем вход на блоки (строки/фрагменты), каждый блок → блок AST → рендер в HTML.

```
src/
  ├─ blocks.rs   — разбиение на заголовки, списки, код, параграфы
  ├─ inline.rs   — обработка **bold**, *italic*, [link](url), `code`
  └─ render.rs   — блок → <h1>, <ul>, <pre>, <p>
```

**Ключевые крейты:** `regex` (опционально), иначе — ручной сканер по символам.

**Этапы.**
1. Заголовки `# .. ######`;
2. `**bold**` и `*italic*`;
3. Списки `- item`;
4. Кодовые блоки ` ``` `;
5. Ссылки и изображения;
6. Таблицы (сложный шаг, `| a | b |`).

**Чек-лист.**
- [ ] Кодовые блоки не обрабатываются внутри кавычки как markdown (не трогаем `**` внутри ` ``` `)
- [ ] HTML-экранирование `<` и `&` в обычном тексте (защита от XSS)
- [ ] Пустой вход → пустой HTML
- [ ] Снапшот-тесты через `insta` (удобно для регрессий)

4. `search` по заголовку/URL;
5. `tags` — фильтрация по тегам.

**Чек-лист.**
- [ ] Данные переживают перезапуск (persist работает)
- [ ] Повторный `add` с тем же URL — либо dedup, либо явный предупреждение
- [ ] Пустой/отсутствующий файл не падает
- [ ] Корректное `edit` тегов

## 15. Статистический пакет «statkit»

**Постановка задачи.** Библиотека статистики: среднее, медиана, дисперсия, стд. отклонение, перцентили, корреляция; с тестами и (позже) бенчами.

**Архитектура.** Чистая библиотека функций над `&[f64]`, возвращающих `Option`/`Result` для пустых входов.

```
lib.rs
  └─ mean, median, variance, std_dev
  └─ percentile(sorted, p)
  └─ linear_regression(xs, ys) -> (slope, intercept)
```

**Ключевые крейты:** только `std`.

**Этапы.**
1. `mean`, `median` (сортировка);
2. `variance` (однопроходный и двухпроходный алгоритм);
3. `std_dev`;
4. `percentile`;
5. `linear_regression`;
6. Документация и doc-tests.

**Чек-лист.**
- [ ] Пустой вход → `None`/`Err`, а не `NaN`/паника
- [ ] `median` чётного/нечётного размера корректен
- [ ] Числовая устойчивость (не вычитать большие числа напрямую при вычислении дисперсии — использовать формулу, устойчивую к катастрофической отмене)
- [ ] doc-tests документируют поведение

## 16. Файловый синхронизатор «snap»

**Постановка задачи.** Инструмент, сравнивающий две папки и выводящий различия (новые/удалённые/изменённые) либо копирующий изменения. Учит рекурсивному обходу, hashing, сравнению.

**Архитектура.**

```
main.rs  (--src, --dst, --diff | --mirror)
  └─ walk.rs      рекурсивный обход → Vec<PathEntry { path, size, hash }>
  └─ diff.rs      сравнение двух снимков → DiffOps { add, remove, modify }
  └─ mirror.rs    применение oper-ций
```

**Ключевые крейты:** `std::fs`, `std::collections::HashSet`, `md5`/`blake3` (хеш).

**Этапы.**
1. Обход директории с размером и хешем файла;
2. Сравнение по (путь, размер, хеш);
3. Вывод differences;
4. `--mirror` — копирование/удаление до состояния цели.

**Чек-лист.**
- [ ] Симлинки не ломают обход (не следовать рекурсивно)
- [ ] Большие файлы не вычитываются целиком в память (стриминг хеша)
- [ ] Режим `--dry-run` показывает план без изменений
- [ ] Подтверждение перед необратимыми операциями (`rm`)

## 17. Обработчик ошибок: служебный «errkit»

**Постановка задачи.** Библиотека-пример правильной обработки ошибок: пользовательский тип ошибки через `thiserror`, богатый контекст через `anyhow`, и единый вывод в `main`. Отдельный мини-проект потому, что обработка ошибок — сквозная тема всех проектов.

**Архитектура.**

```
lib.rs
  └─ error.rs   #[derive(thiserror::Error)] enum LibError { Io, Parse, NotFound }
  └─ ops.rs     функции, возвращающие Result<_, LibError>
bin.rs
  └─ main()     -> anyhow::Result<()>
```

**Ключевые крейты:** `thiserror` (библиотечный тип), `anyhow` (бинарник), `thiserror`.

**Этапы.**
1. Определите `LibError` через `thiserror` с читаемыми сообщениями;
2. Напишите функции, использующие `?` и `map_err`;
3. В `main` используйте `anyhow::Context` для контекста;
4. Настройте `main → Result<(), anyhow::Error>`;
5. Добавьте `From`-конверсии и тест на цепочку ошибок.

**Чек-лист.**
- [ ] Ошибки не «глотаются» (не `unwrap` в библиотеке)
- [ ] Каждый вариант `LibError` имеет понятное `Display`
- [ ] `anyhow` не используется в публичном API библиотеки (только `thiserror`)
- [ ] Вывод ошибки в `main` читаемый (с причиной через `{:#}`)
- [ ] Тесты проверяют сообщения ошибок

## 18. Чат по TCP «chatroom»

**Постановка задачи.** Консольный многопользовательский чат: клиент подключается к серверу, отправляет сообщения, получает сообщения других. Распределяем broadcast между клиентами.

**Архитектура.**

```
server/
  └─ main.rs     TcpListener + mpsc для broadcast
  └─ client.rs   каждый клиент — отдельный поток/задача
client/
  └─ main.rs     stdin + recv в двух потоках
```

**Ключевые крейты:** `tokio` (или `std::thread` + `mpsc`), `serde` (формат сообщений `{ name, text }`).

**Этапы.**
1. Сервер принимает клиентов;
2. Ввод с stdin клиента и отправка;
3. Broadcast: каждое сообщение шлётся всем остальным;
4. Обработка отключения клиента;
5. Имена пользователей.

**Чек-лист.**
- [ ] Отключение одного клиента не роняет сервер
- [ ] Бродкаст не блокирует одного медленного клиента (буфер ограничен)
- [ ] Сообщения из разных клиентов не перемешиваются (small writes атомарны или через lock)
- [ ] Проблемы сокета (резкий разрыв) обработаны

**Архитектура.**

src/

**Ключевые крейты:** `rusqlite` (или `sqlx`), `serde`, `thiserror`.

**Этапы.**

**Чек-лист.**
- [ ] CRUD работает для двух разных моделей (User, Post)
- [ ] Параметризованные запросы (без SQL-инъекций)
- [ ] Откат транзакции при ошибке
- [ ] Миграции идемпотентны

## 20. Web-сервис «blog-api» (итоговый)

**Постановка задачи.** Полноценный web-сервис: CRUD для статей, аутентификация (jwt), база данных, тесты. Объединяет `todo-api`, `errkit`, `sorm` и layer'ы.

**Архитектура (layered):**

```
src/
  ├─ main.rs         запуск, router
  ├─ routes/         articles.rs, auth.rs
  ├─ services/       бизнес-логика
  ├─ repos/          доступ к БД (sqlx)
  ├─ models/         struct Article, User (serde)
  └─ error.rs        ApiError → HTTP статус
```

**Ключевые крейты:** `axum`, `tokio`, `sqlx`, `serde`, `jsonwebtoken`, `argon2` (hash), `tower-http`.

**Этапы.**
1. CRUD статей с PostgreSQL/SQLite;
2. Регистрация/логин с hash-паролями;
3. JWT-аутентификация (middleware);
4. Валидация входных данных;
5. Интеграционные тесты через `oneshot` + тестовая БД.

**Чек-лист.**
- [ ] Пароли хранятся как hash (`argon2`), не в открытом виде
- [ ] Middleware защиты защищает приватные маршруты
- [ ] Ошибки сервиса маппятся в корректные HTTP-статусы
- [ ] Миграции применяются автоматически при старте
- [ ] Тесты изолированы (отдельная тестовая БД)
