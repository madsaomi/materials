# Rust — Проектная стратегия обучения

Проектный подход: не учить Rust «по порядку», а строить **путь проектов**, каждый из которых подтягивает знания конкретного юнита. Рекомендуемый маршрут: **CLI → web → игра → сервис**. Здесь — как этот путь работает и как он связан с юнитами базы.

---

## Принцип: учимся, решая задачи

Проект — это «живой» контекст для новых понятий. Вместо «выучу трейты, потом напишу код» делаем наоборот: **пишем проект, который требует трейтов, и по ходу их осваиваем**.

| Проектный шаг | Какое понятие втягивается |
|---------------|---------------------------|
| надоело писать `if let Some(x)` много раз | `?`, `Option::and_then` |
| код повторяется для числа и строки | generics + трейты |
| два потока пишут в одну HashMap | `Arc<Mutex<>>`, `RwLock` |
| сервер виснет на медленном клиенте | async/await, tokio |
| парсить вложенные выражения нельзя без ссылок | `Box`, рекурсивный enum |

## Путь «CLI → web → игра → сервис»

### Этап 1: CLI — закрепить синтаксис и владение

**Что:** утилиты командной строки с вводом-выводом и файлами.
**Юниты:** Unit 1 (синтаксис, владение, строки), Unit 2 (структуры, enum, коллекции).

**Цели этапа:**
- уверенно владеть ownership/borrowing — без этого ни один проект не сядет;
- `Result`/`?`/`unwrap_or` вместо паники;
- структура `lib` + `bin`;
- работа с `fs` и путями.

**Проекты:** генератор паролей, файловый менеджер, csvread, bookmarklet, statkit.

**Выходной критерий:** вы написали CLI, который не паникует на неверном вводе, читает/пишет файлы и имеет юнит-тесты.

### Этап 2: web — сеть и асинхронность

**Что:** HTTP-клиент и сервер; сначала на `TcpListener`, потом на фреймворке.
**Юниты:** Unit 3 (трейты, конкурентность, async/await).

**Цели этапа:**
- понять HTTP «по байтам» через `TcpListener`;
- освоить `reqwest` (клиент) и `axum` (сервер);
- `serde` для JSON;
- `Arc`/`Mutex`/`RwLock` для разделяемого состояния;
- `tokio` и `spawn`.

**Проекты:** HTTP-клиент miniq, сервер на TcpListener, todo-api, kvstore.

**Выходной критерий:** запустили локальный сервер, `curl` к нему работает, обработка ошибок сети корректна.

### Этап 3: игра — моделирование состояния и событийный цикл

**Что:** развлечение, которое требует продуманного состояния и обработки ввода.
**Юниты:** Unit 2–3 (enum, struct, коллекции, конкурентность ввода).

**Цели этапа:**
- enum как модель состояния (статусы, клетки, объекты);
- событийный цикл (input + render);
- TUI-рендеринг;
- частоты/состояние через HashMap.

**Проекты:** Game of Life, ratatui-TODO, «Угадай число», chatroom (как «сетевая игра»).

**Выходной критерий:** интерактивное приложение с управлением и повторяемостью.

### Этап 4: сервис — инженерный итог

**Что:** полноценный сервис или инструмент с БД, авторизацией, тестами, публикацией.
**Юниты:** все + details.md (трейты, сети, бд, кодогенерация).

**Цели этапа:**
- layered-архитектура;
- БД через `sqlx`/`rusqlite`;
- `thiserror` + `anyhow` во всей цепочке;
- интеграционные тесты;
- `cargo publish` реального крейта.

**Проекты:** blog-api, sorm, интерпретатор lingo.

**Выходной критерий:** работающий продукт, который можно показать, задокументировать и (для lib) опубликовать.

## Схема связи проектов и юнитов

```
Unit 1 (основы)
   ├─ пароли, файловый менеджер, Game of Life    ← этап CLI
   └──────────────────────────────────────────────▶ Unit 2 (enum/struct)
                                                       ├─ csvread, arith, statkit
                                                       └────────────────────▶ Unit 3 (трейты/async)
                                                                            ├─ maxreq, todo-api, kvstore
                                                                            ├─ workerpool, logstat
                                                                            └────────────────────▶ details.md
                                                                                                 ├─ lingo, sorm, blog-api
                                                                                                 └─ компилятор, бенчмаркер
```

Каждый юнит «отвечает» своему этапу: Unit 1 даёт базу для CLI, Unit 2 — для структурированных библиотек, Unit 3 — для сетевых и конкурентных вещей, details.md — для экспертных (макросы, unsafe, производительность).

## Как выбирать следующий проект

Задайте себе три вопроса:

1. **Что я не умею, но хочу?** (например, «не умею async» → проект с tokio);
2. **Каким юнитом это закрывается?** (связь проекта с юнитом из таблицы ниже);
3. **Насколько это сложнее предыдущего?** (не прыгайте больше чем на один уровень).

Если проект слишком лёгкий — добавьте фичу (например, TTL к kvstore). Если слишком сложный — оставьте «скелет», а фичи потом.

## Режим регулярной практики

Два «ритма»:

- **Спринт (проект):** 1–2 недели на проект с фиче-вехами и тесты. Итог — законченный бинарник/крейт.
- **Мини-вылазка (15–30 мин):** одна задача из `unit-0X/practice.md` или маленькое рефакторинг-упражнение. Итог — закрепление приёма.

Небольшие повторяющиеся действия (переписать парсер с нуля, добавить тест, познакомиться с новым крейтом) работают лучше больших марафонов. Проект без тестов — «черновик»; добавьте хотя бы один тест на ключевую фичу.

## Антипаттерны проектного обучения

| Антипаттерн | Почему плохо | Как исправить |
|-------------|--------------|---------------|
| Начать с самого сложного (компилятор) | Разочарование, брошенный проект | Начните с CLI паролями |
| Переписывать всё с нуля вместо расширения | Потеря времени, нет «накопления» | Расширяйте существующий |
| Никаких тестов | Регрессии незаметны | Тест на каждую веху |
| Копировать решение дословно | Ничему не учит | Напишите по памяти позже |
| Прыгать уровни | Путаница в понятиях | Один уровень за раз |
| Игнорировать clippy/fmt | Нечистый код копится | `-- -D warnings` с самого начала |

## Идеи для следующего уровня (после пути)

- **Мини-async-runtime**: свой планировщик задач на `tokio`-внутренностях;
- **Свой `Vec<T>`** через `unsafe` (аллокация, `ptr::write/read`);
- **Derive-макрос** `#[derive(JsonSerde)]` (proc-macro);
- **Компилятор** в LLVM IR или WASM;
- **FFI**: вызов C-функции из Rust;
- **Embedded**: на Raspberry Pi Pico через `embedded-hal`.

Каждый из них — прямое продолжение части `details.md` про unsafe, макросы и FFI.

## Вывод

Путь «CLI → web → игра → сервис» строится так, чтобы каждый следующий этап **опирался на понятия, закреплённые на предыдущем**. Проект — это не «бонус после теории», а **основной двигатель** обучения: теорию (юниты) мы подтягиваем ровно тогда, когда она нужна проекту, и запоминаем её через практическое применение.
