# Rust — Чек-листы проверки кода и самопроверки

Два инструмента для самоконтроля: **чек-листы проверки кода** (по категориям) и **20 вопросов для самопроверки** (общая проверка понимания и готовности).

---

## Чек-лист проверки кода: основное

### Владение и заимствование

- [ ] Нет лишних `clone()` — вместо них заимствование (`&`)
- [ ] `String`/`Vec` перемещаются только когда это нужно (не в горячих цепочках)
- [ ] Нет `&mut` конфликтов, которые можно было бы обойти перестановкой
- [ ] Ссылки не хранятся дольше, чем данные (нет dangling)
- [ ] Нет ненужных `Box`/`Rc`/`Arc` там, где достаточно ссылки или `&`

### Обработка ошибок

- [ ] Ввод пользователя не «разворачивается» через `unwrap`/`expect`
- [ ] `unwrap` появляется только там, где ошибка реально невозможна (и с обоснованием)
- [ ] Ошибки несут контекст (`with_context("/путь")`, `Context`)
- [ ] Библиотека использует `thiserror` (точный тип), а не `anyhow`
- [ ] `main` возвращает `Result` и печатает ошибку в stderr, а не паникует

### Безопасность

- [ ] Пути из ввода не позволяют path traversal (`..`)
- [ ] SQL запросы — параметризованные (без конкатенации строк)
- [ ] Пароли хешируются, а не хранятся открыто
- [ ] Нет вывода секретов в логи
- [ ] `cargo audit` не выдаёт критических уязвимостей в зависимостях

### Конкурентность

- [ ] Разделяемое состояние под `Arc<Mutex>`/`Arc<RwLock>` корректно (не гонка)
- [ ] Потоки/таски не образуют взаимоблокировку (нет захвата двух локов в разном порядке)
- [ ] Канал/бродкаст не блокирует на медленном получателе (буфер ограничен)
- [ ] При graceful shutdown происходит очистка (файлы закрыты, снапшот записан)
- [ ] `Send`/`Sync` проверены компилятором (никакая структура не «утекла» в поток)

### Тесты

- [ ] Есть юнит-тесты на нетривиальные функции
- [ ] Есть интеграционные тесты на публичный API
- [ ] Покрыты граничные случаи (пустой вход, ноль, максимум)
- [ ] Тесты на ошибки (невалидные данные → `Err`)
- [ ] Doc-тесты проходят (`cargo test` зелёный)

### Стиль и чистота

- [ ] `cargo fmt --check` чистый
- [ ] `cargo clippy -- -D warnings` без замечаний
- [ ] Нет мёртвого кода (неиспользуемые функции/импорты)
- [ ] Публичное API задокументировано (`missing_docs` не ругается)
- [ ] Именование консистентно (snake_case для функций/переменных, CamelCase для типов)

### Производительность

- [ ] Нет лишних аллокаций в горячем цикле (`with_capacity`)
- [ ] Release-профиль оптимизирован (опционально для финальной сборки)
- [ ] Для больших данных — `rayon` там, где CPU-bound
- [ ] Нет квадратичных паттернов (вложенная конкатенация строк в цикле)

## Чек-лист «перед премьерой проекта»

- [ ] Проект собирается `cargo build --release` без ошибок
- [ ] `cargo test` проходит целиком
- [ ] `cargo clippy -- -D warnings` чистый
- [ ] `cargo fmt` применён
- [ ] Руководство по запуску (README или doc) есть
- [ ] Ошибки ввода понятны пользователю
- [ ] Для библиотеки — README, license, description готовы к публикации
- [ ] `cargo publish --dry-run` прошёл (для крейтов)
- [ ] Основной сценарий протестирован «от руки»
- [ ] Побочный сценарий (нет файла, пустой ввод) обработан без паники

## 20 вопросов для самопроверки

Ответьте письменно (или устно) — правильных «коротких» ответов нет, важна глубина. К каждому вопросу указано, к какому юниту он относится.

### Владение и типы (Unit 1)

**1.** Что происходит с `s` в `let s = String::from("a"); let t = s;`? Почему `i32` так не работает?
**2.** Чем `let mut x = 5;` отличается от `let x = 6;` (shadowing)?
**3.** Почему нельзя сделать `s[0]` для `String`, но можно `v[0]` для `Vec<char>`?
**4.** Что вернёт `vec.get(10)` на векторе из 5 элементов — и почему это лучше `vec[10]`?

### enum, Result, ошибки (Unit 2)

**5.** Опишите, как `Option<T>` заменяет `null`. Приведите пример, где `Option::and_then` избавляет от вложенных `if let`.
**6.** Что делает оператор `?` и в чём разница между его поведением для `Result` и для `Option`?
**7.** Владея `Result<i32, ParseIntError>`, как получить `i32` без паники? Назовите три способа.
**8.** Почему `enum Tree { Node(Box<Tree>, Box<Tree>) }` требует `Box`, а `enum Direction { Left, Right }` — нет?

### Трейты и generics (Unit 3)

**9.** Что такое «реализация по умолчанию» трейта и как супертрейт (`trait B: A`) ограничивает?
**10.** Чем `fn f<T: Trait>(x: T)` отличается от `fn f(x: impl Trait)`? Когда нужен только второй?
**11.** Для чего `#[derive(Debug, Clone, PartialEq)]`? Что произойдёт, если их не вывести?
**12.** В чём разница `Box<dyn Trait>` (динамический) и `impl Trait`/generic (статический)? Когда `dyn` нужен?

### Коллекции и итераторы (Unit 2/3)

**13.** Как `HashMap::entry(k).or_insert(v)` «умнее», чем простая проверка `contains_key` + `insert`?
**14.** Чем `iter()` от `into_iter()`? Что потребляет при этом коллекция?
**15.** Почему цепочки итераторов (`.map`/`.filter`) бесплатны по аллокациям — и когда появляется аллокация?

### Сеть и конкурентность (Unit 3)

**16.** Что произойдёт, если сервер обрабатывает клиентов в одном потоке, а один клиент молчит?
**17.** Зачем разделять состояние между потоками через `Arc<Mutex<>>`, а не просто передавать ссылку?
**18.** Почему `rayon` подходит для CPU-задач, а `tokio` — для I/O? Приведите по одному примеру.

### Архитектура и процесс (все юниты)

**19.** Почему лучше вынести логику в `lib.rs`, а `main.rs` оставить тонким?
**20.** Опишите, как бы вы опубликовали библиотеку на crates.io (какие шаги и что проверять).

## Ключи-подсказки (не «ответы»)

1. `s` перемещается в `t`; `i32` реализует `Copy`, поэтому копируется.
2. `mut` меняет значение на месте; shadowing создаёт новую переменную (можно менять тип).
3. `String` — UTF-8 байты, индекс может попасть внутрь символа; `Vec<char>` индексируется по элементам.
4. `vec.get(10)` → `None` (безопасно); `vec[10]` → паника (panic).
5. `Option` — явная «возможность отсутствия»; смотрите `first_word` через `split_whitespace().next()`.
6. `?` ранний возврат ошибки; для `Result` — возвращает `Err`, для `Option` — `None`.
7. `unwrap_or`, `unwrap_or_else`, `map_err`+`?`.
8. `Box` даёт фиксированный размер рекурсивному типу; `Direction` без полей имеет точный размер.
9. Метод с телом прямо в трейте; супертрейт требует реализации родителя.
10. `T: Trait` параметризует тип (его может указывать вызывающий); `impl Trait` анонимен.
11. Генерируют реализацию трейта (вывод `{:?}`, копирование, сравнение); без них нужно писать вручную.
12. `dyn` — тип-эрзац для объектов, размер в `Box`; `impl`/generic — мономорфизация, без vtable.
13. `entry` делает один поиск, а не два, и даёт доступ к значению.
14. `iter()` заимствует; `into_iter()` потребляет коллекцию (по значению).
15. Ленивые итераторы не выделяют память; `collect()` — итоговая аллокация.
16. Одиноманный поток заблокируется на чтении первого клиента; нужен `spawn`/неблок. I/O.
17. `Arc` — множественное владение; `Mutex` — исключительный доступ; ссылки не могут жить в потоках-долгожителях без владения.
18. rayon — деление данных на части для потоков; tokio — конкурентное ожидание I/O без удержания потока.
19. `lib` тестируема и переиспользуема; `bin` — тонкая обвязка ввода-вывода.
20. Имя уникально, license/description/README, `cargo publish --dry-run`, `cargo login`, `cargo publish`.

## Как пользоваться чек-листами

- **Перед каждой вехой** — прогоните чек-лист «основное» по написанному фрагменту;
- **Перед «премьерой»** — полный чек-лист на готовом проекте;
- **Раз в месяц** — 20 вопросов самопроверки; если на любой «затык» — перечитайте соответствующий юнит и закрепите мини-проектом.

Наличие одного неисправленного `clippy`-замечания не «валит» учебный проект, но разумно фиксировать его перед сдачей/публикацией — это дисциплина, которая окупится на больших кодовых базах.
