# Railway и GitHub Pages

Проверено 26 октября 2026 года. Текущее приложение — Next.js с серверными страницами
и API. [Результаты локальной проверки](reports/session040/README.md).

| Площадка | Текущее состояние |
|---|---|
| Railway | Для серверного запуска подготовлен Dockerfile со standalone-сборкой. Ниже указаны настройки сервиса. |
| GitHub Pages | Текущий серверный вариант несовместим; статической сборки и workflow публикации в репозитории нет. |

## Railway через Dockerfile

В настройках сервиса, подключённого к этому репозиторию:

1. Корень проекта — корень репозитория, где находятся Dockerfile и package.json.
2. Используйте сборку из Dockerfile. Railway умеет обнаруживать его автоматически;
   не задавайте прежние команды Flask, requirements.txt или gunicorn.
3. Custom Start Command оставьте пустым: образ уже запускает `node server.js`.
4. Укажите Healthcheck Path: `/healthz`.
5. Сервер слушает `0.0.0.0` и порт из `PORT`. Railway передаёт `PORT` сервису;
   отдельное жёсткое значение 5000 для Railway не требуется. В образе 5000 — значение
   по умолчанию для самостоятельного запуска контейнера.
6. Для публичного доступа создайте домен сервиса в Networking. Настройки самого
   сервиса и публикация выполняются в Railway, не командой локальной Git-подготовки.

Dockerfile использует Node.js 22, pnpm 11.25.0, установку по lockfile и
`NEXT_STANDALONE=1`. В runtime отдельно копируются public/ и .next/static/,
поскольку Next.js не включает их в standalone автоматически. Заметки knowledge/
и legacy_paths.json включены через outputFileTracingIncludes.

Источники: [Railway: Dockerfiles](https://docs.railway.com/builds/dockerfiles),
[Railway: PORT и healthcheck](https://docs.railway.com/deployments/healthchecks),
[Next.js: standalone и локальные ресурсы](https://nextjs.org/docs/app/api-reference/config/next-config-js/output).

Для запуска без Docker после обычного `pnpm build` используется `pnpm start`:
scripts/start.mjs передаёт PORT в Next.js и привязывается к 0.0.0.0. Standalone-образ
использует свой server.js; подменять его командой pnpm start в runtime-образе не нужно.

Контроль после публикации: `/healthz`, `/`, `/api/search.json` (1348 записей),
страница заметки, `/api/search?q=...`, `/api/preview/...`, CSS/JS и старый адрес
с query-параметрами. Заметки входят в образ: для публикации изменений нужен новый
деплой. База данных и постоянный диск для текущего чтения библиотеки не требуются.

## Почему текущая версия не запускается на GitHub Pages

[GitHub Pages размещает статические HTML/CSS/JS](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages).
Сейчас в проекте:

- Главная страница и документы помечены force-dynamic; каталог строится по
  серверным searchParams, а динамический путь документа не имеет generateStaticParams.
- Поиск читает параметры запроса; предпросмотр и индекс заметок обслуживаются
  серверными Route Handlers. Кэш читает файлы knowledge/ в Node.js.
- Старые адреса используют серверный permanentRedirect с сохранением параметров.
- Адреса ресурсов, документов и API начинаются с `/`. Для стандартного проектного
  сайта этого репозитория под `/materials/` нужна отдельная обработка префикса.
- Папки .github/workflows/ и команды статического экспорта нет.

[Next.js перечисляет ограничения статического экспорта](https://nextjs.org/docs/app/guides/static-exports):
динамические маршруты без generateStaticParams, обработчики с входящим Request
и серверные перенаправления требуют другого решения. Установка одного output:export
или добавление deploy-pages workflow не переносит существующие функции в статику.

Для отдельной версии Pages потребуется генерировать документы и навигационные
данные при сборке, выполнять фильтры каталога/поиск/предпросмотр в браузере и учитывать
`/materials/` во всех ссылках и ресурсах. Старым адресам понадобятся статические
страницы перехода с переносом query/hash; механизм серверных 308 при этом изменится.
Это отдельная адаптация приложения. В рамках проверки скриптов она не выполнялась;
неработающий workflow публикации не добавлялся.

Локальная проверка Node/standalone не подтверждает выполнение Linux-контейнера
или настройки удалённого сервиса. Фактический Docker build и деплой на площадки
отмечаются отдельно в отчёте.
