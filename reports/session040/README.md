next.config.ts, серверные страницы и API. Ошибок в командах текущего Node-запуска

## Railway: локальная проверка пройдена

- Именно scripts/start.mjs запущен с PORT=5002. Сервер слушал 0.0.0.0;
  /healthz и браузерный скрипт вернули 200.
- Изолированная папка повторяла состав COPY исходников Dockerfile. Зависимости
  установлены pnpm 11.25.0 с --offline --frozen-lockfile из существующего кэша:
  скачиваний 0, исходные зависимости и lockfile не менялись.
- Штатная команда `NEXT_STANDALONE=1 pnpm build` прошла с Next.js 16.4.2,
  Turbopack и Node.js 24.22.1. В standalone вошли все 1348 заметок с исходными SHA256
  и идентичная карта 1217 прежних адресов.
- Исходный server.js standalone запущен с PORT=5003, HOSTNAME=0.0.0.0 и пустым
  NODE_PATH. Родительский node_modules в тестовой папке заранее переименован;
  у 25 внутренних ссылок пакета нет целей за пределами standalone.
  Public и .next/static скопированы по схеме runtime-стадии Dockerfile.
- Standalone прошёл 28 HTTP-проверок: 12 страниц грамматики обеих версий совпали
  с Markdown; проверены каталог, поиск 1348, предпросмотр,404,308 с параметрами,
  CSS/JS, framework-chunk, Python-курс. Healthcheck с Host:healthcheck.railway.app
  вернул 200. Повторяющиеся tag=a&tag=b сохранены в перенаправлении.

Это 28 проверок standalone и 2 отдельные проверки скрипта обычного запуска,
всего 30 HTTP-проверок. Протоколы: [сборка](build.json), [start.mjs](start.json),
[standalone HTTP](standalone-http.json).

Первая диагностическая сборка переиспользовала зависимости через внешний junction
и пропустила 27 трассируемых файлов; она не использована как доказательство готового
пакета. Повтор с зависимостями внутри копии устранил это предупреждение.
Попытка распрямить ссылки pnpm в другой runtime-копии нарушила поиск @swc/helpers;
эта копия также исключена из итогового теста. Проверен исходный standalone с
сохранённой структурой ссылок и отключённым подхватом зависимостей родителя.
Конфигурация приложения ради обхода этих особенностей тестовой Windows-копии
не менялась.

Docker CLI на этом компьютере отсутствует. Linux-контейнер с Node.js 22,
доступность registry/Corepack при удалённой сборке, настройки аккаунта Railway
и фактический облачный деплой здесь не проверялись. Локальный standalone-тест
не выдаётся за выполненный Docker build или удалённый деплой.

## GitHub Pages: текущая версия несовместима

В репозитории нет .github/workflows и статической сборки Pages.
Главная и документы force-dynamic, путь документов не имеет generateStaticParams,
поиск зависит от Request, прежние адреса используют серверные 308.
Ресурсы, /doc и /api используют абсолютный корневой путь; для стандартного
проектного сайта /materials/ нужна отдельная обработка префикса.

Это сопоставлено с [официальными ограничениями статического экспорта Next.js](https://nextjs.org/docs/app/guides/static-exports)
и [устройством GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages).
Одно добавление workflow не переносит поиск, каталог и серверные переходы в статику.
Настройки удалённого репозитория Pages не проверялись; вывод относится к текущему
локальному приложению и имеющимся в нём скриптам. [Машинная карта](pages.json).

В рамках просьбы проверить скрипты полная статическая адаптация не выполнялась.
Неработающий Pages workflow не добавлялся; инструкции теперь явно различают
поддерживаемый Node-запуск и требующую отдельной реализации версию Pages.
